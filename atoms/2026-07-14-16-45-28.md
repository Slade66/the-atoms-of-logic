# ID 设计：从存储主键到公开身份

## 一、ID 的分层设计

- **分层原则：** 同一资源可以同时拥有数据库主键、公开 ID 和用户可见编号；三个身份面向不同边界，不必共用一个值。

- **数据库主键：** 用于数据库内部定位和关联数据，重点追求较低的存储成本和较高的索引效率。

- **公开 ID：** 也就是 API 标识，用于让客户端指定要操作的资源，并支持跨数据库合并。

- **用户可见编号：** 用于识别、搜索和沟通，需要容易朗读和复制。例如：“帮我看看任务 `TASK-20260714-008`。”

## 二、`public_id` 的定位与设计原则

- **公开身份：** `public_id` 跨越数据库、API、日志和客户端边界，长期稳定地代表一个资源。

- **全局唯一：** 数据库分表或合并时，不会发生公开 ID 冲突。

- **与内部实现解耦：** `public_id` 不依赖数据库自增值；数据迁移时，数据库主键可以改变，API 标识保持不变。

- **可安全公开：** `public_id` 可以出现在 URL、日志和响应中，不会暴露业务数据量和创建顺序。

- **容易识别：** 人和程序都能从 ID 中判断资源类型。

- **容易比较：** 使用固定格式和固定长度，并排除容易混淆的字符。

## 三、`public_id` 的格式设计

### 3.1 基本格式

- **资源前缀：** 仅凭随机部分无法判断 ID 属于任务、习惯还是时间轴，因此使用“资源类型 + 下划线 + 随机部分”的格式。

    ```text
    {资源类型}_{随机部分}
    ```

- **格式示例：** 不同资源使用不同的类型前缀。

    ```text
    task_7K3M9Q2X8F4D
    habit_4W8N2C7R9P3K
    timeline_6F2D8X5M7Q9J
    ```

- **随机部分：** 使用 Crockford Base32 编码，排除容易混淆的字符 `I`、`L`、`O`、`U`。

- **存储成本：** 完整存储前缀会多占几个字节，但能让查询、日志和排错更加直接，成本可以忽略。

### 3.2 资源前缀的作用

- **人工识别：** ID 被单独复制到响应、日志、剪贴板或错误信息中时，人仍然能直接判断资源类型。

- **类型校验：** 程序可以根据前缀，在查询数据库前拒绝类型错误。例如，任务接口收到 `habit` ID 时直接返回错误。

    ```http
    GET /api/tasks/habit_7K3M9Q2X8F4D
    ```

    ```json
    {
        "error": "invalid task id"
    }
    ```

- **命名空间隔离：** 前缀定义了 ID 所属的资源命名空间；不同资源的随机部分即使相同，完整 ID 也不会冲突。

## 四、不同场景下的 ID 选择

- **单体应用、单库：** 数据库主键使用自增 `BIGINT`。

- **分布式服务：** 内部 ID 使用 Snowflake 生成的 64 位整数。

- **多端离线创建后同步：** 使用 UUIDv7 或 ULID，让客户端可以独立生成 ID。

- **用户可见业务单号：** 使用独立的业务编号，不直接暴露数据库主键。

- **公开分享链接：** 使用随机外部 ID，避免暴露内部资源编号。
