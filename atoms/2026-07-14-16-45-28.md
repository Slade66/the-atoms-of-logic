# ID 设计：内部主键、公开标识与 ULID 规范

## 一、同一资源可以有多种 ID

- **分层原则：** 同一资源可以同时拥有数据库主键、公开 ID 和用户可见编号。三者服务的边界不同，不必共用同一个值；是否合并取决于具体方案。

- **数据库主键：** 数据库内部用它定位记录和关联数据，重点是存储成本与索引效率。

- **公开 ID：** API、日志和客户端用它长期代表一个资源；它需要能跨数据库、跨服务和跨数据合并场景保持唯一。

- **用户编号：** 面向识别、搜索和沟通，需要容易朗读和复制。例如“帮我看看任务 `TASK-20260714-008`”。它应独立于数据库主键。

## 二、公开 ID 应承担的职责

### 2.1 稳定的跨边界身份

- **长期稳定：** `public_id` 不应依赖数据库自增值。迁移数据或替换内部主键时，API 标识仍保持不变。

- **合并安全：** 数据库分表或合并时，公开 ID 不应与已有资源冲突。

- **公开边界：** 公开 ID 可以出现在 URL、日志和响应中。它不应暴露连续的数据库自增序号或直接泄露数据量。

### 2.2 能被人和程序识别

- **资源类型：** ID 中应包含资源类型，使人和程序都能判断它属于任务、习惯还是时间轴。

- **类型校验：** 服务端可在查询数据库前检查资源前缀；例如任务接口收到 `habit-...` 时直接拒绝。

    ```http
    GET /api/tasks/habit-01ARZ3NDEKTSV4RRFFQ69G5FAV
    ```

    ```json
    {
        "error": "invalid task id"
    }
    ```

- **命名空间：** 资源前缀定义 ID 的命名空间。即使不同资源恰好使用相同的 ULID，完整 ID 仍然不同。

## 三、公开 ID 的最终格式

### 3.1 格式与组成

- **统一格式：** 使用 `<resource>-<ULID>`，例如 `task-01ARZ3NDEKTSV4RRFFQ69G5FAV`。

- **资源前缀：** 使用小写单数，例如 `task`、`habit`、`timeline`。前缀使独立出现的 ID 仍可被人工识别。

- **分隔符：** 使用 `-`，不使用 `_`。在 SQL `LIKE` 中，`_` 表示任意单个字符；例如 `LIKE 'task_%'` 并不按字面量匹配下划线。使用 `-` 可避免每次查询都处理转义。

- **ULID 部分：** 使用 26 位大写 Crockford Base32 编码。字符集排除容易混淆的 `I`、`L`、`O`、`U`，便于人工复制和核对。

### 3.2 可识别性与格式约束

- **格式一致：** 每种资源都有固定的前缀和固定长度的 ULID 部分，便于程序校验和人眼比对。

- **直接排错：** 把完整 ID 写入响应、日志、剪贴板或错误信息后，仍可直接看出资源类型，无需额外查询。

## 四、按场景选择 ID 策略

- **单体应用、单库：** 内部主键可使用自增 `BIGINT`，以获得简单紧凑的索引。

    - 示例：`42`。

- **分布式服务：** 内部 ID 可使用 Snowflake 生成的 64 位整数。

    - 示例：`1729382256910270464`。

- **多端离线同步：** 可使用 UUIDv7 或 ULID，让客户端能够独立生成 ID。

    - 示例：`01ARZ3NDEKTSV4RRFFQ69G5FAV`。

- **用户可见单号：** 应使用独立的业务编号，不直接暴露数据库主键。

    - 示例：`TASK-20260714-008`。

- **公开分享链接：** 应使用随机外部 ID，避免暴露内部资源编号；若使用 ULID，需接受其近似时间信息可被推断的边界。

    - 示例：`share-7K3M9Q2X8F4D`。
