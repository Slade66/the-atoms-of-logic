# 如何升级项目的 Go 版本

- **先分清两件事：** 本机装的 Go，和项目 `go.mod` 里的 `go` 行，是两套版本。升级本机不会改 `go.mod`；改 `go.mod` 也不等于本机已经装了那个版本。

- **升级本机 Homebrew 装的 Go 版本：** 先执行 `which go`，输出 `/opt/homebrew/bin/go` 说明是 Homebrew 安装的。步骤见 [Homebrew 如何升级 Go 的版本？](2026-08-10-10-16-38.md)。

## `go.mod` 里的 `go` 行有什么用

- **是什么：** 这一行是这个模块的语言版本声明，表示这份代码按哪一版 Go 来理解，不是“本机装了哪个 Go”。

- **管什么：** 编译本仓库里的包时，编译器按这一行选择语言版本，决定能写哪些语法。本机即使是 Go 1.25，只要 `go.mod` 仍是 `1.24.3`，代码仍按 1.24 的语言语义编译。要用 1.25 的新语法，必须先把这一行升上去。

- **从 Go 1.21 起是硬门槛：** 拿本机工具链和这一行比较——

    - **本机更低：** 默认 `GOTOOLCHAIN=auto` 时，`go` 命令会去下更新的工具链；关掉自动下载（本机太旧又不允许自动切换）则会直接报错退出，拒绝构建。

    - **本机更高：** 可以直接编，但代码仍按 1.24 语义，不会自动变成 1.25。

## `go.mod` 里的 `toolchain` 行有什么用

- **是什么：** 声明这个模块建议使用的 Go 工具链版本。它不是把编译器精确锁死在这一版；只有当前默认工具链比它旧时，才会触发工具链切换。当前工具链如果比它新，就继续使用当前更高版本。

- **比如：** `go.mod` 里写成：

    ```text
    go 1.24.3
    toolchain go1.25.1
    ```

    - **意思是：** 代码仍按 1.24 语言规则编译（不能用 1.25 新语法），同时建议至少使用 `go1.25.1` 工具链。若当前工具链是 `go1.24.x`，在 `GOTOOLCHAIN=auto` 下会切换到满足要求的新工具链；若当前已经是 `go1.26`，则继续使用 `go1.26`，不会降级到 `go1.25.1`。

- **约束：** `toolchain` 的版本不能低于 `go` 行。

- **需不需要写 `toolchain` 行？** 希望“至少用 xx 版的编译器”（例如它修过某个 bug）时才写。没有 `toolchain` 时，最低工具链就退化为 go 行本身。

## 环境变量 `GOTOOLCHAIN`

- **`GOTOOLCHAIN=auto`（Go 1.21 起的默认）：** `go build` / `go test` 会先比较当前默认工具链和 `go.mod` 的要求：

    1. 算出最少需要哪个版本（`go` 行或 `toolchain` 行里更高的那个）

    2. 当前工具链已经够新，就直接继续用当前版本，不切换，也不会为了匹配 `toolchain` 而降级

    3. 当前工具链太旧时，才尝试切换到满足要求的新工具链；先查找 PATH 中可用的工具链，找不到时再下载并缓存对应工具链

    4. 换成选中的新 `go` 再执行原来的命令

    - 真正编译的可能是刚下载的 Go 版本，也可能是 PATH 里已有的更高版本，不一定是 `toolchain` 行写的那个精确版本。

    - **前提：** 本机这个 `go` 本身至少是 1.21。只有 1.21+ 才懂 “自动换工具链”。若本机是 `1.20`，它不会去下载，只会报版本太旧。

- **`GOTOOLCHAIN=local`：** 只用本机已经装好的 Go，禁止再下载、禁止切换，避免构建时偷偷下载另一套编译器。

    - 这时若本机是 `1.23`、模块要 `1.24.3`，命令会直接失败，不会构建，也不会去网上拉工具链，类似：

    ```text
    go: go.mod requires go >= 1.24.3 (running go 1.23.6; GOTOOLCHAIN=local)
    ```

- **一段话总结：** 当前 Go 已经满足 `go.mod` 的最低要求时，就继续使用当前版本；只有当前工具链太旧且允许自动切换时，才会寻找或下载够新的工具链继续编。如果禁止这种自动切换，而本机版本又不够，就只能报错。

## 怎么升级 `go.mod` 里的 `go` 版本？

- **推荐写法：** `go get go@1.26`。写语言版本即可，会落到该系列最新 release；它会改 `go.mod` 的 `go` 行，必要时一并处理 `toolchain` 行。升到官方最新发布用 `go get go@latest`。

- **不会换掉本机的 Go：** `go get go@1.26.5` 只改这个项目的 `go.mod`，不会覆盖 PATH、Homebrew 或 `/usr/local/go` 里已经装好的那套。

    - **例外：** 只有本机 Go 比目标版本旧、且 `GOTOOLCHAIN=auto` 时，才可能再下一套工具链，缓存到模块缓存里多一份编译器，供 `go` 命令临时调用。版本够了，一般不会再下，只会改 `go.mod`。例如本机是 `1.26.5`、`go.mod` 还是 `1.24.3` 时执行 `go get go@latest`：

        ```zsh
        daily-archiver on  main via 🐹 v1.26.5
        ❯ go get go@latest
        go: updating go.mod requires go >= 1.26.6; switching to go1.26.6
        go: downloading go1.26.6 (darwin/arm64)
        go: upgraded go 1.24.3 => 1.26.6

        daily-archiver on  main [!] via 🐹 v1.26.6 took 19s
        ❯ go version
        go version go1.26.6 darwin/arm64
        ```

- **其它写法：**

    ```bash
    go get go@1.25.1           # 指定具体小版本
    go get toolchain@go1.25.1  # 设置建议工具链版本，不改语言版本
    go get toolchain@none      # 删掉 toolchain 这一行
    go mod edit -go=1.26       # 只改 go 行、不下载
    ```

## Dockerfile 和 go.mod 的 Go 版本要对齐

- **坑：** 流水线做容器构建时，镜像里的 Go 版本和 `go.mod` 要求的最低工具链对不上，导致的构建失败或者构建变慢（后台在下载工具链）问题。

- **`go 1.24.13` 同时确立语法版本和编译器版本：** 语法按 1.24；编译器最低要用 `go1.24.13` 这套工具链。同系列的 `1.24.3` 也不够。

- **Dockerfile 不写精确版本会漂移：** 例如 `FROM golang:1.24`。`1.24` 是浮动 tag，打出来是 `go1.24.3` 还是 `go1.24.13`，取决于 Docker Hub 当时推的是哪一版。

- **对不上会怎样：** 对不上就报错，或在构建时再下一套编译器（容器里默认往往也是 `GOTOOLCHAIN=auto`）。

    - **再下一套：** `go build` 发现镜像里的 Go 版本和 `go.mod` 不一样，就在构建过程中再下一套 `go`。表面上能编过，但你以为用的是镜像里的 Go，其实又拉了一套；要能访问 GOPROXY / go.dev，内网、离线、`GOPROXY=off` 会失败；构建也会变慢。

    - **直接报错：** `go.mod` 写了 `toolchain` 版本、容器对不上、又不能自动切换时，直接报错退出。

- **结论：** `go.mod` 和 Dockerfile 的 Go 版本必须对齐。

- **做法：** Dockerfile 用精确 tag，例如 `FROM golang:1.24.13`，和 `go.mod` 的 `go` 行一致。每次升级 `go` 指令，同步改 Dockerfile，不要用 `1.24` 这种浮动 tag。
