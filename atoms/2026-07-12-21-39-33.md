# Eunomia 项目 Go 后端目录结构：按业务模块聚合的模块化单体

## 一、目录结构的设计目标

- **设计目标：** 目录结构要服务于日常开发，大部分改动应收敛在一个业务目录内，同时保持模块边界清晰，避免循环依赖和公共代码污染。衡量标准是完成一个需求需要跨越多少个顶层目录，跳转越少，结构越贴合业务的变化方式。

- **Go 项目惯例：** Go 没有唯一固定的目录结构，但服务端项目通常用 `cmd/` 保存程序入口，用 `internal/` 保存不对外暴露的业务代码。Go 官方对 Server Project 的建议也是把可执行程序放进 `cmd/`，把服务逻辑放进 `internal/`。

    ```text
    cmd/       # 程序入口
    internal/  # 项目内部代码
    ```

## 二、Eunomia 的目录组织方案

### 2.1 按业务模块聚合

- **项目形态：** Eunomia 是一个模块化单体，单个后端同时包含任务管理、时间轴和习惯打卡等多个业务模块。

- **组织原则：** 先按业务模块拆目录，模块内部再用文件区分职责，而不是在整个项目中全局拆成 `handler/`、`service/`、`repository/`。

- **推荐结构：**

    ```text
    eunomia/
    ├── cmd/
    │   └── server/
    │       └── main.go
    ├── internal/
    │   ├── app/
    │   │   └── app.go
    │   ├── task/
    │   │   ├── model.go
    │   │   ├── handler.go
    │   │   ├── service.go
    │   │   ├── repository.go
    │   │   └── mysql_repository.go
    │   ├── timeline/
    │   │   ├── model.go
    │   │   ├── handler.go
    │   │   ├── service.go
    │   │   ├── repository.go
    │   │   └── mysql_repository.go
    │   ├── habit/
    │   │   ├── model.go
    │   │   ├── handler.go
    │   │   ├── service.go
    │   │   ├── repository.go
    │   │   └── mysql_repository.go
    │   ├── httpserver/
    │   │   └── router.go
    │   ├── database/
    │   │   └── mysql.go
    │   └── config/
    │       └── config.go
    ├── migrations/
    │   ├── 001_create_tasks.sql
    │   ├── 002_create_timeline.sql
    │   └── 003_create_habits.sql
    ├── go.mod
    └── README.md
    ```

### 2.2 模块与文件职责

- **业务模块：** `task` 负责任务管理，`timeline` 负责时间轴记录，`habit` 负责习惯打卡。开发某个功能时，其模型、业务逻辑、接口和数据访问代码都集中在对应目录中。

- **模块内分层：** `handler.go` 处理 HTTP 请求，`service.go` 承载业务规则，`repository.go` 定义数据访问能力，`mysql_repository.go` 提供 MySQL 实现，`model.go` 保存该模块的领域对象和状态定义。

    ```text
    handler.go → service.go → repository.go → MySQL
                         ↓
                      model.go
    ```

- **公共基础设施：** `httpserver` 负责路由和 HTTP Server，`database` 负责数据库连接，`config` 负责配置读取。这些目录只保存跨模块共用的基础能力，不承载具体业务逻辑。

### 2.3 应用装配与启动

- **装配点：** `internal/app/app.go` 负责把各部分组装成完整应用。

    1. 读取配置。
    2. 连接数据库。
    3. 创建各业务模块。
    4. 注册路由。
    5. 启动和关闭 HTTP 服务。

- **启动入口：** `cmd/server/main.go` 应该保持很薄，只负责启动应用并处理启动失败。

    ```go
    func main() {
        if err := app.Run(); err != nil {
            log.Fatal(err)
        }
    }
    ```

### 2.4 目录结构的演进规则

- **当前阶段：** 按业务模块分目录，在模块内部用文件区分职责。一个功能的主要改动应尽量收敛在一个模块目录中。

- **模块变大后：** 当单个模块的文件数量和复杂度明显增加时，再在该模块内部拆分子目录，而不是提前给所有模块套上复杂分层。

    ```text
    internal/task/
    ├── domain/
    ├── application/
    ├── storage/
    └── transport/
    ```

- **最终原则：** 先按业务模块聚合，再在模块内部按职责分层；目录结构应该跟随业务的变化方式，而不是机械模仿框架模板。

## 三、为什么不直接照搬 Kratos 的全局分层

### 3.1 两种项目的结构前提

- **Kratos 微服务：** Kratos 主要面向“一个仓库对应一个微服务”的场景。微服务通常已经围绕一个业务领域完成拆分，因此整个项目本身就是一个业务模块，项目内部适合按技术职责分层。

- **Eunomia 单体：** 一个服务包含任务管理、时间轴和习惯打卡等多个独立业务模块，因此应该优先按业务边界组织，让同一个功能的代码保持内聚。

- **典型结构：** 例如订单服务的整个仓库都围绕订单领域展开。

    ```text
    order-service/
    └── internal/
        ├── service/
        ├── biz/
        ├── data/
        └── server/
    ```

- **分层职责：** Kratos 用 `service / biz / data` 隔离传输协议、业务规则和基础设施。

    ```text
    HTTP / gRPC
        ↓
    service   API DTO 转换、用例编排
        ↓
    biz       领域模型、业务规则、Repository 接口
        ↓
    data      MySQL、Redis、第三方服务的具体实现
    ```

    - `service` 实现 Protobuf 生成的 HTTP/gRPC 接口，把 DTO 转换成领域对象，不承载复杂业务。
    - `biz` 保存核心业务规则，并定义数据访问接口。
    - `data` 实现 `biz` 定义的接口，把 MySQL、Redis 等基础设施与业务隔离。
    - `server` 创建 HTTP/gRPC Server 并注册服务。

### 3.2 全局分层在单体项目中的问题

- **功能被拆散：** 如果 Eunomia 直接照搬 Kratos，一个业务功能会同时散落在 `service`、`biz` 和 `data` 三个顶层目录中。

    ```text
    internal/
    ├── service/
    │   ├── task.go
    │   ├── timeline.go
    │   └── habit.go
    ├── biz/
    │   ├── task.go
    │   ├── timeline.go
    │   └── habit.go
    └── data/
        ├── task.go
        ├── timeline.go
        └── habit.go
    ```

- **修改成本：** 修改一个功能时，需要在三四个目录之间反复横跳；当项目有十几个业务模块时，每个技术层目录下都会堆积十几个同级文件，查找和理解成本会持续增加。
