# V2V 迁移后 Linux 网络失效的根因

- **核心问题：** V2V 迁移后，Linux Guest OS 看到的虚拟网卡硬件变了，但系统里的网络配置还在找旧硬件，所以旧配置应用不到新网卡上，最终表现为网卡没有 IP、地址漂移、路由丢失等问题。

## 一、迁移后 Guest OS 看到的是一块新网卡，会给它分配新的网卡名

- **硬件变化：** 源端 VMware 常见网卡是 `vmxnet3` 或 `e1000`，迁到 KVM/FusionCompute 后变成 `virtio-net`；PCI 槽位、MAC、驱动也一起变化，Guest Linux 会把它识别成一块新的网络设备。

- **网卡名变化：** Linux 给网卡起名时，PCI 位置经常会参与命名；迁移前 Guest Linux 看到的是 VMware 网卡，所以按旧 PCI 位置命名，常见接口名可能是 `ens192` 或 `eno16777728`；迁移后 Guest Linux 看到的是 KVM/FusionCompute 的 virtio 网卡，所以按新 PCI 位置重新命名，接口名可能变成 `ens3` 或 `enp1s0`。

    ```text
    迁移前：VMware 虚拟机

    Guest Linux 看到的虚拟硬件
       |
       |-- PCI 位置 A -> VMware 网卡 vmxnet3/e1000
                        |
                        v
                      Linux 起名：ens192

    迁移后：KVM / FusionCompute 虚拟机

    Guest Linux 看到的虚拟硬件
       |
       |-- PCI 位置 B -> KVM 网卡 virtio-net
                        |
                        v
                      Linux 起名：ens3
    ```

## 二、旧配置为什么套不上新网卡

- **配置绑定对象：** 旧网络配置通常会绑定接口名、MAC、配置文件名等信息，比如 `ifcfg-ens192`、`DEVICE=ens192`、`HWADDR=旧 MAC`。

- **迁移后的错位：** 迁移后真实网卡可能变成 `ens3`，MAC 也可能变成新值，但旧配置还在找 `ens192` 和旧 MAC。结果就是系统能看到新网卡，却不会把旧配置应用到它上面。

    - **正常匹配：**

    ```text
    系统里真实网卡名：ens192
    配置文件：ifcfg-ens192
    DEVICE=ens192
    HWADDR=当前网卡 MAC

    => 匹配成功，IP 配上去
    ```

    - **迁移失配：**

    ```text
    系统里真实网卡名：ens3
    旧配置文件：ifcfg-ens192
    DEVICE=ens192
    HWADDR=旧 VMware MAC

    => 名字对不上，MAC 也可能对不上，配置不上去
    ```

## 三、哪些配置会因为网卡名、MAC 或 IP 改变而失效

| 会失效的配置 | 它是什么 | 依赖的什么被改了 | 绑死示例 | 故障表现 |
| --- | --- | --- | --- | --- |
| `ifcfg` 网卡配置 | RHEL / CentOS 常见的网卡配置；麒麟部分环境也兼容这种方式 | 接口名从 `ens192` 变成 `ens3`，或 MAC 变了 | `ifcfg-ens192`、`DEVICE=ens192`、`HWADDR=旧 MAC`、`IPADDR=10.0.0.10`、`GATEWAY=10.0.0.1` | 新网卡没有 IP；默认网关丢失；DNS 不生效 |
| NetworkManager keyfile | NetworkManager 的连接配置文件，常见于 RHEL 9+、CentOS Stream、部分麒麟环境 | 连接配置还指向旧接口名或旧 MAC | `interface-name=ens192`、`mac-address=旧 MAC`、`address1=10.0.0.10/24,10.0.0.1` | 配置文件还在，但连接激活不到新网卡上 |
| Ubuntu `netplan` | Ubuntu 常见的网络声明文件 | YAML 里写死了旧接口名或旧 MAC | `ethernets: ens192:`、`match: macaddress: 旧 MAC`、`routes: [{to: default, via: 10.0.0.1}]` | `netplan apply` 后新网卡没有旧 IP、网关、DNS |
| 静态路由 | 指定某个网段应该从哪个网卡、哪个网关走 | 路由文件名或路由内容还指向旧接口名 | `route-ens192`、`default via 10.0.0.1 dev ens192`、`10.10.0.0/16 via 10.0.0.254 dev ens192` | 同网段通，跨网段不通；默认路由不对 |
| 策略路由 | 按来源 IP、目的网段、路由表等条件选出口 | 规则或路由表还绑着旧接口名 | `rule-ens192`、`from 10.0.0.10 table 100`、`default via 10.0.0.1 dev ens192 table 100` | 多网卡、多出口、业务网访问异常 |
| udev / systemd 命名规则 | 手工规定“哪个硬件应该叫什么网卡名” | 旧 MAC、旧 PCI 路径或旧接口名变了 | `ATTR{address}=="旧 MAC", NAME="eth0"`、`MACAddress=旧 MAC`、`Name=ens192` | 预期的名字没出现；新网卡被命成别的名字 |
| Bond / Bridge / VLAN | 聚合口、网桥、VLAN 子接口的成员关系 | 成员网卡名或父接口名变了 | `MASTER=bond0`、`SLAVE=yes`、`PHYSDEV=ens192`、`bridge-ports ens192` | 聚合口、网桥、VLAN 起不来；业务网络断 |
| 防火墙规则 | `firewalld`、`iptables`、`nftables` 里按接口放行或拦截流量 | 接口名变了 | `firewall-cmd --zone=public --add-interface=ens192`、`iptables -A INPUT -i ens192 -j ACCEPT`、`iifname "ens192"` | 放行规则没有套到新网卡上，流量被挡 |
| 高可用 VIP | `keepalived`、Pacemaker 或脚本把虚拟 IP 挂到指定网卡上 | VIP 绑定的接口名变了，或旧 IP 没配到新网卡上 | `interface ens192`、`virtual_ipaddress { 10.0.0.100/24 dev ens192 }` | VIP 没挂上；主备切换后业务不通 |
| 服务监听配置 | Nginx、HAProxy、Redis、MySQL、PostgreSQL、BIND、vsftpd 等服务监听指定 IP | 旧业务 IP 没配到新网卡上；它通常不直接依赖网卡名或 MAC | `nginx listen 10.0.0.10:80`、`redis bind 10.0.0.10`、`vsftpd listen_address=10.0.0.10` | 服务启动失败，或服务启动了但业务 IP 访问不到 |
| 监控、脚本、自动化 | 巡检脚本、Ansible、Prometheus / Grafana 告警、备份或安全脚本 | 写死的接口名、MAC、IP 变了 | `ip addr show ens192`、`nmcli dev show ens192`、`device="ens192"` | 告警失真；自动修复脚本改错对象；巡检误判 |
